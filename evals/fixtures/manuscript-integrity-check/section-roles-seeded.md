# **Just-DNA-Lite: a Local-First, Open-Source Platform for Personal Genome Annotation and Polygenic Risk Scoring**

*Excerpt: Sections 1.1, 2, 3.1, 3.2.1, 3.3 and 3.4, most of Sections 3.2, 4 and 5, Box 1, the tables, the figures, the references and the supplement are not included.*

## **Abstract**

Just-DNA-Lite is the core of an open-source ecosystem for reading a personal genome against published evidence on the user's own computer. Its web platform annotates a whole-genome VCF and computes polygenic risk scores locally, so the genome does not have to be uploaded. Every matched variant links to its reported effect and its sources. What the platform reports comes from modules, versioned tables of variant-trait associations that researchers write without programming. Ready-made modules cover longevity, disease predisposition and drug response. Researchers publish new ones to just-dna-registry, an open registry that works like an app store, where others browse, install and apply them with no software update. The just-module-creator plugin drafts modules from the literature and public databases inside the AI assistant a researcher already uses. Polygenic scores come from just-prs, a library that also works on its own. It places each PGS Catalog score that passes its reference-distribution audit within a reference population matched to the genome's inferred ancestry and shows all models for a trait side by side, so users see where the models agree and differ. AI assistants can also run annotation and scoring through Model Context Protocol servers, and a public demonstration lets anyone try the platform on public genomes.

## **1. Introduction**

### **1.2 Overview of Just-DNA-Lite**

Just-DNA-Lite is a local, open-source platform for annotating a personal genome and computing polygenic scores. We developed it as a ground-up rewrite of Just-DNA-Seq (Kulaga et al., 2024), whose first generation (Generation I), built for longevity research, was a set of annotation and report modules for OakVar, a Python variant-analysis framework derived from OpenCRAVAT (Pagel et al., 2020). Just-DNA-Lite (Generation II) removes the OakVar dependency entirely and uses a standalone annotation engine. It also replaces Python annotation plugins with declarative modules discoverable from configured sources (Section 2.2). Supplementary S1 describes Generation I.

The resulting workflow lets users choose published annotation content, apply it to their own genome and inspect the evidence behind the report. The reusable just-prs scoring library adds polygenic scores and reference-population comparisons to the same web interface. Researchers can contribute new annotation modules through the open-source registry, and Model Context Protocol (MCP) servers let AI assistants call the annotation and scoring operations as tools instead of writing their own analysis code. People with different needs enter this workflow at different points: the main features are listed below, and Box 1 names the user groups and where each starts.

**Key features.**

- **A cleaned PGS Catalog, ready to use.** just-prs mirrors the PGS Catalog's harmonized scoring files as Parquet, with cleaned metadata in which genome-build labels are normalized and published performance metrics are parsed into numbers. Its reference distributions cover 6,117 scores for 778 traits in five 1000 Genomes superpopulations. Each result gives its percentile in the reference population matched to the genome's inferred ancestry, its coverage and a quality label (Section 3.2). Each distribution is audited before release; 860 scores were withheld, 847 of them because most of seven public test genomes fell in the outermost 1% of the reference distribution with scores off its scale, which shows that a real genome's score would not be on the reference scale.
- **An app store for annotation modules.** Modules are data: versioned tables of variant-trait associations with their sources, written as CSV and YAML without code. Researchers publish them to just-dna-registry, and users browse them in the web interface's Module Catalog (Figure 1a), install them and apply them to their genome, with no new software release. On 26 October 2026 the registry held 24 modules from five publishing accounts, the ten defaults of Table 1 and fourteen others (Section 3.4).
- **Fast.** On one workstation, a whole genome is annotated with the ten default modules in 33 to 65 s, 128 to 231 times faster than Generation I's configured workflow (which also runs database annotators), and a rerun on an already normalized genome takes 16 to 20 s. just-prs computes a polygenic score in a median of 0.08 s. In our benchmark configuration, in which PLINK2 was started once per score on four threads and just-prs used sixteen, that is about seven times faster than PLINK2 (Section 4).
- **Three ways in.** The same operations are available from a web interface; from AI assistants (Claude Code, Codex, Cursor and other MCP clients) through two MCP servers and installable plugin skills; and from Python libraries and command-line tools published on PyPI (just-prs, prs-ui, just-dna-format, just-dna-compiler and the just-dna-registry client).
- **Evidence a reader can follow.** Each matched variant in a report leads to its reported effect, the module's conclusion and its sources, and each polygenic score to its PGS Catalog model, coverage and reference population (Figures 1b, 2 and 3).
- **Local.** Annotation and scoring run on the user's computer. Reference data are downloaded; the genome is not uploaded (Section 5.2).

## **3. Algorithm and Implementation: Annotation Modules and Polygenic Scoring**

### **3.2 Polygenic Risk Scores**

For traits with several published models, the interface displays the scores together, each with its percentile, coverage and quality label, beside a summary across the models and the reference population, so that users can inspect agreement and disagreement (Figure 3).

Polygenic risk scores (PRS) aggregate the effects of many variants into a single weighted sum (Lambert et al., 2021), which is read as a position within a reference population for a given trait. We developed the just-prs library (github.com/dna-seq/just-prs) as the PRS computation engine for Just-DNA-Lite; it can also be used on its own (Section 3.2.1). just-prs scores the harmonized scoring files of the PGS Catalog (Lambert et al., 2021; harmonized files documented at https://www.pgscatalog.org/downloads/): a file-level audit of just-prs 0.10.1 against the PGS Catalog release of 17 September 2026 placed 6,910 of 6,991 files in Table S5's “as specified” category, 76 in “approximated” and 5 in “cannot be scored”. These categories assess scoring-file compatibility, using a 10% absolute-weight threshold for omitted or ambiguous rows. The first category can therefore include files with some omitted weight; it does not establish complete coverage in an individual genome or predictive validity.

**A catalogue that works out of the box.** The scoring files, metadata and reference distributions that just-prs reads are prepared once and downloaded on first use from HuggingFace (datasets `just-dna-seq/pgs-catalog` and `just-dna-seq/prs-percentiles`), so users do not assemble them. The metadata are cleaned: nine genome-build labels are mapped to three builds or "not reported", and performance metrics that the Catalog publishes as text, such as "1.55 [1.52,1.58]", are parsed into estimates, confidence intervals and standard errors for odds ratios, hazard ratios, betas, the area under the receiver operating characteristic curve (AUROC) and C-index. Each score's 1000 Genomes reference distribution (described below) is audited before release. In the reference-distribution release of 2 September 2026, 6,117 of 6,977 scores passed and 860 were withheld. For 847 of them, at least four of seven public test genomes (all seven, for 783) fell in the outermost 1% of the reference distribution at either end and the scores failed a scale check (across the test genomes, a median of at least six standard deviations from the reference mean, or a median of fewer than half of the score's variants matched in them), which means that a real genome's score is not on the reference scale; the rest were withheld because too few of their variants matched the reference panel or their reference distribution had zero or undefined spread. The 6,117 scores map to 778 traits of the Experimental Factor Ontology.

Each computed score carries a quality label: *Very low* when the genome covers less than 20% of the score's absolute weight; *High* when it covers at least 50% and the score's AUROC reported in the Catalog, taken from its largest European-ancestry evaluation or, without one, its largest evaluation, is at least 0.7; otherwise *Moderate*, except *Low* for a score developed on another genome build whose AUROC is below 0.6 or not reported. Such a score also has 0.05 subtracted from its AUROC before these thresholds are applied. For 2,282 scores in the curation published on 27 September 2026, just-prs further records what a higher score means (higher or lower risk, or more or less of a measured trait), annotated from the source publications by AI agents (the curation skills of the just-prs plugin for Claude Code, run with Anthropic's Claude Opus models) and pending expert review.

Generation I derived its PRS percentiles by simulating 10,000 genotypes from pooled gnomAD allele frequencies and fitting a normal distribution to the simulated scores (Kulaga et al., 2024). just-prs instead scores the 3,202 individuals of the 1000 Genomes reference panel (Byrska-Bishop et al., 2022) with each model, summarizes the observed scores as a mean and standard deviation for each of five superpopulations (African, AFR; admixed American, AMR; East Asian, EAS; European, EUR; South Asian, SAS), and places a user's score on the corresponding normal distribution, so the reference reflects real genotypes and their linkage structure rather than simulated ones. The reference superpopulation is inferred from the genome (Section 3.2.2) and the user can choose another; the percentile is the user's position within that distribution.

### **3.2.2 Ancestry Inference**

The reference superpopulation is chosen by a k-nearest-neighbour classifier on principal components, built once from the 1000 Genomes high-coverage panel (Byrska-Bishop et al., 2022) and downloaded as a fixed model (HuggingFace dataset `just-dna-seq/pgs-catalog`, folder `data/ancestry`). Its training data are the panel's unrelated individuals, 2,575 after related ones were removed with a KING kinship list (Manichaikul et al., 2010), each labelled with one of five superpopulations (AFR, AMR, EAS, EUR, SAS), and 53,526 autosomal biallelic SNVs kept after quality control and linkage pruning in PLINK2 (Chang et al., 2015): minor allele frequency at least 0.05, Hardy–Weinberg *P* at least 10⁻⁴, and *r*² below 0.05 within windows of 1,000 variants. A principal component analysis of these genotypes defines the space. A user's genome is projected into it with the online augmentation, decomposition and Procrustes method of FRAPOSA (Zhang et al., 2020), and its superpopulation is the majority among its 20 nearest reference individuals on the first 10 components. Model sites a variant-only VCF does not list are coded as homozygous reference, and sites whose alleles disagree with the model as missing. There is no separate test set. In leave-one-out classification of the reference individuals, on principal components computed from the whole panel, 99.65% were assigned their own superpopulation (2,566 of 2,575); seven of the nine misassigned individuals belong to the admixed American group, of whom 344 of 351 were assigned correctly. This measures how well the five groups separate within the panel; accuracy on admixed genomes and on populations the panel does not sample was not measured (Section 5.4). When fewer than 20% of the model's sites can be used, the ancestry is reported as unknown and the user chooses the reference. Sites coded as homozygous reference count as used, so for exome or array input, where most model sites are not read, the call rests largely on assumed genotypes.

## **4. Benchmarking and Validation**

The benchmarks in this section measure how fast the platform annotates a genome and computes polygenic scores, how much memory it uses, and how closely its scoring engines agree with each other and with an external tool. They do not test whether the annotations themselves are correct.

### **4.1 Annotation Speed**

On Anton Kulaga's published call set, the median full Generation II run took 33.2 s against 6,005.4 s for Generation I, an approximately 181-fold speedup; across the three call sets Generation I ran on, it was 128- to 231-fold (Table 2). Most Generation I runs on the other two call sets were made with the desktop in light use (Supplementary S2). Against a whole-genome reference database the gap narrows. Generation II with Ensembl annotation on took a median of 103.1 s and Generation I with dbSNP alone 3,537.2 s, about 34-fold (two runs each; 24- to 57-fold across pairs of runs). These ratios apply to these configurations and these inputs, rather than to OakVar generally. A warm run took a median of 16.3 s.

### **4.2 PRS Computation**

The two just-prs engines agreed closely on the benchmark genome, while agreement with PLINK2 depended on how variants were matched (Supplementary S3). The allele-aware rerun with just-prs 0.10.2 is reported below and in Tables 3 and 4.

We benchmarked the DuckDB and Polars engines of just-prs against the external tool PLINK2 (Chang et al., 2015) on 100 PGS Catalog scores (listed in Supplementary S3) using Anton Kulaga's published whole-genome VCF of Section 4.1 (4,661,444 records with FILTER PASS or unset, GRCh38; Zenodo 18370498). Engines, timing and memory measurement are those of the benchmark script of just-prs 0.10.1, run through a harness described in Supplementary S3 on the workstation of Table S6. In both runs PLINK2 used four compute threads and the just-prs engines their default thread pools (one thread per logical CPU, 16 in both runs). Each PLINK2 time also includes starting a separate process, so the speed comparison describes this configuration rather than equal resources. ## **5. Discussion**

### **5.6 Conclusion**

Just-DNA-Lite gives people and researchers a local way to read a genome against published evidence. It offers a cleaned PGS Catalog, with ancestry-matched percentiles for 6,117 scores and quality labels, a registry of installable annotation modules that grows as researchers publish them, whole-genome annotation in about a minute, and the same operations from a web interface, AI assistants and Python libraries. The reported benchmarks show annotation 128 to 231 times faster than the configured workflow of the OakVar-based Generation I system run on the same machine and close numerical agreement between scoring engines, on four call sets from three people for annotation and one for scoring. Evaluation across individuals, reference populations and matched-variant sets remains necessary to establish the broader reliability of these workflows. The platform provides infrastructure for research and education, without establishing clinical validity for the findings it reports. Researchers can begin with the public-data demonstration, inspect the sources behind a report, and then apply or extend the same workflow locally for their own research questions.
